    装饰器模式 (Decorator Pattern)

    理念：动态地给对象添加功能，而不是通过继承产生无数个子类。

    实现：处理流的构造函数接收一个“流对象”作为参数，把它包起来，增加新功能后，再暴露同样的接口。

    效果：可以像俄罗斯套娃一样层层包装。

    java安全基础

    jdk安全分水岭

    1. JDK 9：模块系统与反射限制 (分水岭)

    • 核心变化：引入 Java Platform Module System (JPMS)。

    • 影响

      ：

      • 封装性增强：JDK 内部的包（如 java.lang, java.util）默认不再对 unnamed module（普通用户代码）开放。
      • 反射受限：即使使用 setAccessible(true)，如果目标模块没有 opens，反射也会失败。这就是你遇到报错的直接原因。
      • 目的：防止恶意代码通过反射篡改 JDK 内部核心逻辑，提高平台安全性。

    • 口号：“强封装” (Strong Encapsulation)。

    2. JDK 14 - 16：过渡与清理

    • JDK 14：默认禁止反射访问非 opens 的包（之前在 JDK 9-13 只是警告，可以通过参数忽略，从 14 开始默认报错）。

    • JDK 15 & 16

      ：

      • 移除了 Nashorn JavaScript 引擎（一个常见的攻击面）。
      • 禁用了 TLS 1.0 和 1.1（过时的不安全协议）。
      • 开始逐步废弃 SecurityManager（因为配置复杂且容易被绕过，官方打算用更细粒度的机制替代）。

    3. JDK 17 (LTS)：全面加固 (当前主流)

    • 核心变化：彻底落实 JDK 9 的愿景，并清理历史包袱。

    • 影响

      ：

      • SecurityManager 废弃：标记为 deprecated，官方明确不建议在新应用中使用，未来版本将移除。
      • 禁止动态代理访问非公共接口：进一步限制反射能力。
      • 更强的默认值：许多原本需要手动开启的安全选项现在默认开启。

    • 地位：目前企业级开发的首选 LTS 版本，安全基线很高。

    4. JDK 21 (LTS) 及未来：现代化安全

    • 核心变化：引入 虚拟线程 (Virtual Threads) 的同时，继续收紧底层权限。

    • 影响

      ：

      • 外部函数与内存 API (Foreign Function & Memory API)：取代了不安全的 sun.misc.Unsafe 和 JNI，提供了更受控的内存访问方式。

      • 严格模式：对于未命名的模块访问 JDK 内部 API 的限制更加严格，几乎堵死了所有“旁门左道”。

    ClassLoader加载机制

    通过类加载器ClassLoader 将.class字节码文件加载到JVM的内存中

    并将其转换为java.lang.Class对象

    JVM中有4种类加载器

    1. Bootstrap ClassLoader (引导类加载器)

      加载java的核心api java.util.* java.lang.*

    2. Platform ClassLoader (平台类加载器) jdk8前叫 Extension ClassLoadler (扩展类加载器)

      加载扩展库后平台模块

    3. Application ClassLoader (应用类加载器) jdk8前叫 System ClassLoader (系统类加载器)

      加载用户类路径下的类 application

      默认情况下会启动Appaction ClassLoader

    4. Custom ClassLoader (自定义类加载器)

      继承java.lang.ClassLoader类自行编写

    双亲委派模型

    加载类的时候 类加载器会先请求上层的加载器先去加载类

    ClassLoader类加载过程

    加载

    将类的.class文件读入内存 并创建一个java.lang.Class对象

    将字节码从不同的数据源(class文件 jar包 网络) 转化为二进制字节流加载到内存中

    加载类的时候通过双亲委派的机制 先让上层的ClassLoader先去尝试加载类 如果类加载器找不到 会自动将委托传到下层类加载器 默认的类加载器是Application ClassLoader 通过双亲委托去加载类 如果ApplicationClassLoader 也找不到要加载的类 会尝试使用自定类加载类

    链接

    将类的二进制数据合并到JRE中

    2. 准备

    BCEL类 加载器和Xalan 类加载器

    (java反序列化洞)

    详见BCEL ClassLoader 和 Xalan ClassLoader

    BCEL 是 Apache Jakarta 项目下的一个开源 Java 库，全称是 Byte Code Engineering Library。

    它的唯一目的只有一件事：以编程方式分析、创建和修改 Java 字节码（.class 文件）。

    主要功能

    1. 生成动态代理类

    2. 代码插桩（比如在方法前后自动插入日志或性能监控代码）

    3. 编译器开发（将其他语言编译成 Java 字节码）

    4. 代码混淆器或优化器

    如果把 .class 文件比作“二进制机器码”，BCEL 就是一套允许你用 Java 代码直接编写、修改这些“机器码”的工具包，而不需要手写十六进制数据。

    原理

    BCEL类中的ClassLoader 全限定类名:com.sun.org.apache.bcel.internal.util.ClassLoader

    当BCEL的com.sun.org.apache.bcel.internal.util.ClassLoader.loadClass()加载一个类名中带有$$BCEL$$的类时会截取出$$BCEL$$后面的字符串，然后使用com.sun.org.apache.bcel.internal.classfile.Utility.decode()将字符串解析成类字节码，最后会调用defineClass()注册解码后的类，一旦该类被加载就会触发类中的恶意代码

    适用性

    BCEL 6.0以下

    Oracle自带的BCEL是修改了原始的包名，因此也有兼容性问题，已知支持该特性的JDK版本为：JDK1.5 - 1.7、JDK8 - JDK8u241、JDK9

    动态代理

    Java反射提供了一种类动态代理机制，可以通过代理接口实现类来完成程序无侵入式扩展。

    简单来说，它允许你在程序运行时，“变出”一个代理对象，这个对象拥有和真实对象一样的接口，但在调用真实对象的方法前后，你可以插入额外的逻辑（如日志、事务、权限检查等）

    java.lang.reflect.Proxy java.lang.reflect.InvocationHandler

    java.lang.reflect.Proxy类是通过创建一个新的Java类(类名为com.sun.proxy.$ProxyXXX)的方式来实现无侵入的类方法代理功能的。

    动态代理生成出来的类有如下技术细节和特性：

    1. 动态代理的必须是接口类，通过动态生成一个接口实现类来代理接口的方法调用(反射机制)。
    2. 动态代理类会由java.lang.reflect.Proxy.ProxyClassFactory创建。
    3. ProxyClassFactory会调用sun.misc.ProxyGenerator类生成该类的字节码，并调用java.lang.reflect.Proxy.defineClass0()方法将该类注册到JVM。
    4. 该类继承于java.lang.reflect.Proxy并实现了需要被代理的接口类，因为java.lang.reflect.Proxy类实现了java.io.Serializable接口，所以被代理的类支持序列化/反序列化。
    5. 该类实现了代理接口类(示例中的接口类是com.anbai.sec.proxy.FileSystem)，会通过ProxyGenerator动态生成接口类(FileSystem)的所有方法，
    6. 该类因为实现了代理的接口类，所以当前类是代理的接口类的实例(proxyInstance instanceof FileSystem为true)，但不是代理接口类的实现类的实例(proxyInstance instanceof UnixFileSystem为false)。
    7. 该类方法中包含了被代理的接口类的所有方法，通过调用动态代理处理类(InvocationHandler)的invoke方法获取方法执行结果。
    8. 该类代理的方式重写了java.lang.Object类的toString、hashCode、equals方法。
    9. 如果动过动态代理生成了多个动态代理类，新生成的类名中的0会自增，如com.sun.proxy.$Proxy0/$Proxy1/$Proxy2。

    java反序列化

    序列化就是将java对象转化为二进制数组的形式 便于网络传输

    反序列化就是将二进制数组转变为原来的java对象

    序列化库:

    java.io.Serializeable(内部序列化) java.io.Externalizable(外部序列化)

    序列化与反序列化

    java库中的java.io.ObjectInputStraeam和java.io.ObjectOutputStraeam提供的writeObject()和readObject()实现了序列化与反序列化

    Serializable接口

    序列化对象需要 它的类继承Serializable接口

    对象中的所有属性都会被序列化和反序列化

    某个字段不想被序列化 可以使用transient修饰 静态属性也不会被序列化

    serialVersionUID字段

    一个对象在反序列化的时候 如果序列化串中的uid与当前对象值不同 反序列化会失败

    如果uid没有显示生成 系统会自动生成

    属性的变化都会导致自动生成的serialVersionUID发生变化。如果序列化和反序列化的serialVersionUID不同，则会报序列化版本不同的错误

    反序列化要求

    • 被反序列化的类必须存在。
    • serialVersionUID值必须一致。

    RMI

    RMI(Remote Method Invocation)即Java远程方法调用，RMI用于构建分布式应用程序，RMI实现了Java程序之间跨JVM的远程通信。

    RMI架构

    服务端

    客户端

    注册表

    RMI底层通讯采用了Stub(运行在客户端)和Skeleton(运行在服务端)机制，RMI调用远程方法的大致如下：

    1. RMI客户端在调用远程方法时会先创建Stub(sun.rmi.registry.RegistryImpl_Stub)。
    2. Stub会将Remote对象传递给远程引用层(java.rmi.server.RemoteRef)并创建java.rmi.server.RemoteCall(远程调用)对象。
    3. RemoteCall序列化RMI服务名称，Remote对象。
    4. RMI客户端的远程引用层传输RemoteCall序列化后的请求信息通过Socket连接的方式传输到RMI服务端的远程引用层。
    5. RMI服务端的远程引用层(sun.rmi.server.UnicastServerRef)收到请求会请求传递给Skeleton(sun.rmi.registry.RegistryImpl_Skel#dispatch)。
    6. Skeleton调用RemoteCall反序列化RMI客户端传过来的序列化。
    7. Skeleton处理客户端请求：bind、list、lookup、rebind、unbind，如果是lookup则查找RMI服务名绑定的接口对象，序列化该对象并通过RemoteCall传输到客户端。
    8. RMI客户端反序列化服务端结果，获取远程对象的引用。
    9. RMI客户端调用远程方法，RMI服务端反射调用RMI服务实现类的对应方法并序列化执行结果返回给客户端。
    10. RMI客户端反序列化RMI远程方法调用结果。

    RMI中的核心类UnicastRemoteObject

    主要有3个作用

    1. 开启监听端口 (随机端口)
    2. 自动生成Stub对象
    3. 处理网络请求

    JNDI

    java naming and Director interface (java命名和目录接口) 查找资源提供的一个通用接口

    JNDI使得可以使用统一的代码连接接口

    Naming Service 命名服务

    命名服务将名称和对象进行关联，提供通过名称找到对象的操作，例如：DNS系统将计算机名和IP地址进行关联、文件系统将文件名和文件句柄进行关联等等。

    Directory Service 目录服务

    目录服务是命名服务的扩展，除了提供名称和对象的关联，还允许对象具有属性。目录服务中的对象称之为目录对象。目录服务提供创建、添加、删除目录对象以及修改目录对象属性等操作。

    Reference 引用

    在一些命名服务系统中，系统并不是直接将对象存储在系统中，而是保持对象的引用。引用包含了如何访问实际对象的信息。

    核心类:

    javax.naming.Context

    1. Context 接口 (核心中的核心)

    这是命名服务的根接口，代表一个命名环境。

    • 作用：执行绑定、查找、解绑操作。
      • lookup(String name): 根据名字获取对象。
      • bind(String name, Object obj): 绑定名字和对象。
      • rebind(String name, Object obj): 重新绑定（如果名字存在则覆盖）。
      • unbind(String name): 解除绑定。
      • list(String name): 列出上下文中的名字。

    javax.naming.directory.InitialContext

    2. InitialContext 类

    • 作用：这是 Context 接口的入口点。当你 new InitialContext(env) 时，它会读取环境变量 (env)，确定要连接哪个服务提供商（如 LDAP 还是 RMI），然后初始化具体的上下文对象。
    • 地位：几乎所有 JNDI 操作的起点。

    javax.naming.directory.DirContext

    3. DirContext 接口

    • 作用：继承自 Context，增加了目录服务功能。

    • 特有方法

      ：

      • getAttributes(String name): 获取对象的属性。
      • search(String base, String filter): 强大的搜索功能（类似 SQL 的 WHERE 子句）。
      • modifyAttributes(...): 修改属性。

    jndi注入

    流程:

    客户端通过jndi (lookup()方法) 寻找某个服务对象(RMI,LADP等) -> 服务端的对象为一个Reference对象 返回该对象 ->

    客户端得到该Reference对象 自动的去寻找他的工厂类 并自动的加载指定的工厂类 执行代码

    JNDI允许通过对象工厂 (javax.naming.spi.ObjectFactory)动态加载对象实现

    Reference对象需要继承对象工厂 (javax.naming.spi.ObjectFactory) 改写方法getObjectInstance

    通过lookup()查找对象名称 服务器如果返回Reference对象 客户端则会自动下载并且还可以动态加载远程代码

    当访问的是一个jndi中的reference对象时 会自动下载工厂类 并自动加载该类

    版本限制

    RMI

    • JDK 6u211, 7u201, 8u191 (2018年10月发布)：
      • 限制：默认禁止 com.sun.jndi.rmi.object.trustURLCodebase 和 com.sun.jndi.cosnaming.object.trustURLCodebase 为 true。
      • 影响：RMI 和 COS 协议无法再从远程 HTTP 加载类。
      • 例外：LDAP 协议当时未被完全限制（这是一个疏忽），所以 LDAP 注入依然有效。

    LADP

    JDK 8u292, 11.0.11, 15.0.3, 16.0.2 (2021年4月发布)：

    • 限制：默认禁止 com.sun.jndi.ldap.object.trustURLCodebase。
    • 影响：LDAP 也无法从远程加载类了。
    • 现状：在新版 JDK 上，传统的 Reference + Remote Codebase 攻击链默认失效。

    javassist

    • Javassist 是 Java 字节码编辑库，可以在运行时生成、修改类。
    • 支持动态生成类、方法、字段，也能修改已有类的字节码。
    • 与直接操作字节码相比，提供高层次 API，更易上手。
    • ClassPool
    • CtClass 的容器，用于管理和获取类。
    • 核心方法：getDefault()、get()、makeClass()、insertClassPath()、appendClassPath()。
    • CtClass
    • 表示编译时类，可修改父类、生成字节码、创建静态初始化块。
    • 核心方法：setSuperclass()、toBytecode()、makeClassInitializer()、toClass()。
    • CtMethod / CtField
    • 类似增强版 Method / Field，对方法和字段进行动态修改。
    • 支持修改方法体、插入代码片段、修改修饰符、重命名方法等。
    • 主要功能
    • 读取类信息：获取字段、方法、构造函数。
    • 修改类方法：修改方法体、插入前后代码、修改访问修饰符。
    • 动态创建类：创建新类、添加字段和方法，支持静态初始化块和构造函数。
    • 二进制操作：通过 toBytecode() 获取字节码数组，可写入文件生成 .class。
    • 应用场景
    • 动态代理和 AOP 增强
    • 运行时代码注入
    • 动态类生成
    • 字节码分析与修改
    • 注意点
    • 所有操作都是基于字节码层面进行，生成的文件都是 .class。
    • 可以在 JVM 运行时直接加载生成的类。
    • 支持静态代码块、构造函数及方法前后插入逻辑，非常灵活。
