    装饰器模式 (Decorator Pattern)

    理念：动态地给对象添加功能，而不是通过继承产生无数个子类。

    java安全基础

    jdk安全分水岭

    1. JDK 9：模块系统与反射限制 (分水岭)

    • 核心变化：引入 Java Platform Module System (JPMS)。

    • 影响

      ：

      • 封装性增强：JDK 内部的包（如 java.lang, java.util）默认不再对 unnamed module（普通用户代码）开放。
      • 反射受限：即使使用 setAccessible(true)，如果目标模块没有 opens，反射也会失败。这就是你遇到报错的直接原因。
      • 目的：防止恶意代码通过反射篡改 JDK 内部核心逻辑，提高平台安全性。

    • 口号：“强封装” (Strong Encapsulation)。

    2. JDK 14 - 16：过渡与清理

    • JDK 14：默认禁止反射访问非 opens 的包（之前在 JDK 9-13 只是警告，可以通过参数忽略，从 14 开始默认报错）。

    • JDK 15 & 16

      ：

      • 移除了 Nashorn JavaScript 引擎（一个常见的攻击面）。
      • 禁用了 TLS 1.0 和 1.1（过时的不安全协议）。
      • 开始逐步废弃 SecurityManager（因为配置复杂且容易被绕过，官方打算用更细粒度的机制替代）。

    3. JDK 17 (LTS)：全面加固 (当前主流)

    • 核心变化：彻底落实 JDK 9 的愿景，并清理历史包袱。

    • 影响

      ：

      • SecurityManager 废弃：标记为 deprecated，官方明确不建议在新应用中使用，未来版本将移除。
      • 禁止动态代理访问非公共接口：进一步限制反射能力。
      • 更强的默认值：许多原本需要手动开启的安全选项现在默认开启。

    • 地位：目前企业级开发的首选 LTS 版本，安全基线很高。

    4. JDK 21 (LTS) 及未来：现代化安全

    • 核心变化：引入 虚拟线程 (Virtual Threads) 的同时，继续收紧底层权限。

    • 影响

      ：

      • 外部函数与内存 API (Foreign Function & Memory API)：取代了不安全的 sun.misc.Unsafe 和 JNI，提供了更受控的内存访问方式。

      • 严格模式：对于未命名的模块访问 JDK 内部 API 的限制更加严格，几乎堵死了所有“旁门左道”。

    ClassLoader加载机制

    通过类加载器ClassLoader 将.class字节码文件加载到JVM的内存中

    并将其转换为java.lang.Class对象

    JVM中有4种类加载器

    1. Bootstrap ClassLoader (引导类加载器)

      加载java的核心api java.util.* java.lang.*

    2. Platform ClassLoader (平台类加载器) jdk8前叫 Extension ClassLoadler (扩展类加载器)

      加载扩展库后平台模块

    3. Application ClassLoader (应用类加载器) jdk8前叫 System ClassLoader (系统类加载器)

      加载用户类路径下的类 application

      默认情况下会启动Appaction ClassLoader

    4. Custom ClassLoader (自定义类加载器)

      继承java.lang.ClassLoader类自行编写

    双亲委派模型

    加载类的时候 类加载器会先请求上层的加载器先去加载类

    ClassLoader类加载过程

    加载

    将类的.class文件读入内存 并创建一个java.lang.Class对象

    将字节码从不同的数据源(class文件 jar包 网络) 转化为二进制字节流加载到内存中

    加载类的时候通过双亲委派的机制 先让上层的ClassLoader先去尝试加载类 如果类加载器找不到 会自动将委托传到下层类加载器 默认的类加载器是Application ClassLoader 通过双亲委托去加载类 如果ApplicationClassLoader 也找不到要加载的类 会尝试使用自定类加载类

    链接

    动态代理

    Java反射提供了一种类动态代理机制，可以通过代理接口实现类来完成程序无侵入式扩展。

    简单来说，它允许你在程序运行时，“变出”一个代理对象，这个对象拥有和真实对象一样的接口，但在调用真实对象的方法前后，你可以插入额外的逻辑（如日志、事务、权限检查等）

    java.lang.reflect.Proxy java.lang.reflect.InvocationHandler

    java.lang.reflect.Proxy类是通过创建一个新的Java类(类名为com.sun.proxy.$ProxyXXX)的方式来实现无侵入的类方法代理功能的。

    动态代理生成出来的类有如下技术细节和特性：

    1. 动态代理的必须是接口类，通过动态生成一个接口实现类来代理接口的方法调用(反射机制)。
    2. 动态代理类会由java.lang.reflect.Proxy.ProxyClassFactory创建。
    3. ProxyClassFactory会调用sun.misc.ProxyGenerator类生成该类的字节码，并调用java.lang.reflect.Proxy.defineClass0()方法将该类注册到JVM。
    4. 该类继承于java.lang.reflect.Proxy并实现了需要被代理的接口类，因为java.lang.reflect.Proxy类实现了java.io.Serializable接口，所以被代理的类支持序列化/反序列化。
    5. 该类实现了代理接口类(示例中的接口类是com.anbai.sec.proxy.FileSystem)，会通过ProxyGenerator动态生成接口类(FileSystem)的所有方法，
    6. 该类因为实现了代理的接口类，所以当前类是代理的接口类的实例(proxyInstance instanceof FileSystem为true)，但不是代理接口类的实现类的实例(proxyInstance instanceof UnixFileSystem为false)。
    7. 该类方法中包含了被代理的接口类的所有方法，通过调用动态代理处理类(InvocationHandler)的invoke方法获取方法执行结果。
    8. 该类代理的方式重写了java.lang.Object类的toString、hashCode、equals方法。
    9. 如果动过动态代理生成了多个动态代理类，新生成的类名中的0会自增，如com.sun.proxy.$Proxy0/$Proxy1/$Proxy2。

    RMI架构

    注册表

    RMI底层通讯采用了Stub(运行在客户端)和Skeleton(运行在服务端)机制，RMI调用远程方法的大致如下：

    1. RMI客户端在调用远程方法时会先创建Stub(sun.rmi.registry.RegistryImpl_Stub)。
    2. Stub会将Remote对象传递给远程引用层(java.rmi.server.RemoteRef)并创建java.rmi.server.RemoteCall(远程调用)对象。
    3. RemoteCall序列化RMI服务名称，Remote对象。
    4. RMI客户端的远程引用层传输RemoteCall序列化后的请求信息通过Socket连接的方式传输到RMI服务端的远程引用层。
    5. RMI服务端的远程引用层(sun.rmi.server.UnicastServerRef)收到请求会请求传递给Skeleton(sun.rmi.registry.RegistryImpl_Skel#dispatch)。
    6. Skeleton调用RemoteCall反序列化RMI客户端传过来的序列化。
    7. Skeleton处理客户端请求：bind、list、lookup、rebind、unbind，如果是lookup则查找RMI服务名绑定的接口对象，序列化该对象并通过RemoteCall传输到客户端。
    8. RMI客户端反序列化服务端结果，获取远程对象的引用。
    9. RMI客户端调用远程方法，RMI服务端反射调用RMI服务实现类的对应方法并序列化执行结果返回给客户端。
    10. RMI客户端反序列化RMI远程方法调用结果。

    java agent

    简单来说就是可以动态的修改字节码 hook技术

    JDK1.5开始，Java新增了Instrumentation(Java Agent API)和JVMTI(JVM Tool Interface)功能，允许JVM在加载某个class文件之前对其字节码进行修改，同时也支持对已加载的class(类字节码)进行重新加载(Retransform)。

    1. 启动Java程序时添加-javaagent(Instrumentation API实现方式)或-agentpath/-agentlib(JVMTI的实现方式)参数，如java -javaagent:/data/XXX.jar LingXeTest。

    2. JDK1.6新增了attach(附加方式)方式，可以对运行中的Java进程附加Agent。

    这两种运行方式的最大区别在于第一种方式只能在程序启动时指定Agent文件，而attach方式可以在Java程序运行后根据进程ID动态注入Agent到JVM

    JVMTI 是底层 C++ 接口，Instrumentation API 是基于它封装的、用于开发 Java Agent 的标准 Java 接口，而 Attach API 则是一种能在运行时将 Agent 动态挂载到目标 JVM 的通信机制。

    静态hook

    1. 入口：JVM 启动时带上 -javaagent 参数，JVM 会首先执行 Agent 的 premain 方法。

    2. 注册：在 premain 中，Agent 调用 inst.addTransformer(new MyTransformer())。这相当于给 JVM 的类加载器装了一个“过滤器”。

    3. 拦截：当应用程序尝试加载一个类（例如 com.example.UserService）时，JVM 会先读取该类的 .class 文件字节流。

    4. 转换（Hook 核心）：在类被定义（Define Class）之前，JVM 会调用 MyTransformer 的 transform 方法，并将原始的字节码数组 byte[] 传进来。

    5. 修改

      ：

      • Agent 使用 ASM 或 Javassist 解析这个字节数组。
      • 找到目标方法（如 login）。
      • 在方法体的开头插入代码（如 System.out.println("Start login");），在结尾插入代码（如 System.out.println("End login");）。

    6. 返回：Agent 返回修改后的新字节数组。JVM 拿着这个“被篡改”的字节码去生成 Class 对象。

    7. 结果：应用程序运行 UserService.login() 时，实际上执行的是你植入逻辑后的代码。

    动态hook

    1. 入口：通过 Attach API 将 Agent 动态挂载到正在运行的 JVM 进程上，触发 agentmain 方法。

    2. 执行

      ：

      • 同样注册 Transformer，或者直接使用 inst.retransformClasses(TargetClass.class)。

    3. 触发：JVM 收到指令后，会强制重新加载目标类的字节码，并再次经过 Transformer 的处理流程（同静态 Hook 的 4-6 步）。

    4. 结果

      ：内存中的类定义被替换，新的请求进来时就会执行新的逻辑。

      • 注意：这种方式通常只能修改方法体内部逻辑，不能增加/删除字段或方法。

    环绕方法

    • 通知（Advice）: AOP 框架中的增强处理，通知描述了切面何时执行以及如何执行增强处理，也就是我们上面编写的方法实现。
    • 连接点（join point）: 连接点表示应用执行过程中能够插入切面的一个点，这个点可以是方法的调用、异常的抛出，实际上就是我们在方法执行前或是执行后需要做的内容。
    • 切点（PointCut）: 可以插入增强处理的连接点，可以是方法执行之前也可以方法执行之后，还可以是抛出异常之类的。
    • 切面（Aspect）: 切面是通知和切点的结合，我们之前在xml中定义的就是切面，包括很多信息。
    • 引入（Introduction）：引入允许我们向现有的类添加新的方法或者属性。
    • 织入（Weaving）: 将增强处理添加到目标对象中，并创建一个被增强的对象，我们之前都是在将我们的增强处理添加到目标对象，也就是织入（这名字挺有文艺范的）

    SpringMVC

    Spring MVC 的核心工作流程：

    1. DispatcherServlet (前端控制器)： 所有的请求第一步都会发给它。它就像公司里的前台/前置路由。
    2. HandlerMapping (处理器映射器)： 前台查表，看看这个 URL 归哪个 Controller 管。
    3. Controller (控制器)： 你写的业务代码。它去调用 Service 层处理数据，然后返回一个“结果”。
    4. ModelAndView (结果封装)： 包含了两样东西——要展示的数据（Model）和要去哪个页面（View）。
    5. ViewResolver (视图解析器)： 把逻辑上的页面名（比如 “index”）变成真实的地址（比如 “/WEB-INF/jsp/index.jsp”）。
    6. 渲染返回： 把数据填进页面，发回给浏览器。

    M (Model) 模型： 负责数据。比如从数据库拿数据、处理业务逻辑、保存用户信息。它是程序的“大脑”。

    V (View) 视图： 负责展示。比如 HTML 页面、App 界面、或者是返回给前端的 JSON 数据。它是程序的“脸面”。

    C (Controller) 控制器： 负责调度。它像个中转站：接收用户的请求，告诉 Model 去处理数据，最后决定把哪个 View 给用户看。

    1. Controller 层（控制层 / 表现层）

    • 角色： 餐厅服务员。
    • 职责： 负责接收客人的订单（HTTP 请求），校验一下订单格式对不对，然后把需求传给后厨（Service）。
    • 关键点： 它不应该写复杂的逻辑，只负责“接活儿”和“回话”。
    • 注解： @RestController, @RequestMapping

    2. Service 层（业务逻辑层）

    • 角色： 后厨大厨。
    • 职责： 核心逻辑所在地。比如“下单”这个动作，需要查库存、算折扣、扣余额、发短信。大厨负责把这些散碎的步骤拼凑成一个完整的“业务”。
    • 关键点： 这是最值钱的一层，所有的计算和业务规则都写在这里。
    • 注解： @Service

    3. Repository / DAO 层（数据访问层）

    • 角色： 仓库管理员。
    • 职责： 只负责和数据库打交道。它不关心业务，你告诉它“给我找 ID 为 1 的用户”，它就去执行 SQL 把数据拿回来。
    • 关键点： 在 Spring Data JPA 中通常叫 Repository，在 MyBatis 中通常叫 Mapper。
    • 注解： @Repository, @Mapper

    4. Entity / POJO 层（实体模型层）

    • 角色： 菜单或食材。
    • 职责： 它是数据的载体。比如 User 类，里面定义了用户名、密码、邮箱等字段。它是数据库表在 Java 里的“投影”。
    • 注解： @Entity, @Table

    5. DTO / VO 层（数据传输对象）

    这是为了安全和灵活衍生的“包装”层：

    • DTO (Data Transfer Object)： 前端传给后端的数据（比如注册时只传用户名密码，不需要传 ID）。
    • VO (View Object)： 后端展示给前端的数据（比如返回用户信息时，要把密码字段抹掉）。

    设置注解 @ResponseBody

    使用 @ResponseBody 注解告诉 Spring 将返回值作为响应体处理，而不是视图名称，因此无法进行模 板注入攻击。

    设置重定向 redirect

    当视图名称以 redirect: 前缀开头时，Spring不再使用 Spring ThymeleafView 解析，而是使用 RedirectView 解析，该视图不会执行表达式。但存在 URL 跳转漏洞。

    设置 response 响应

    由于控制器在参数中具有 HttpServletResponse，Spring 认为已经处理了HTTP响应，因此视图名称解 析就不会发生。这个检查存在于 ServletResponseMethodArgumentResolver 类中。
